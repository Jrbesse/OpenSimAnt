## The toolchain: net10.0 and Godot 4.7.2

**Godot 4.6.2 → 4.7.2** (#111, PR #114, merged 2026-11-17). Three files, three lines:
`remake/game/OpenSimAnt.csproj` (`Godot.NET.Sdk/4.6.2` → `4.7.2`, TFM stays `net8.0` in this phase),
`remake/game/project.godot` (`config/features` `"4.6"` → `"4.7"`), and `.github/workflows/release.yml`
(`GODOT_VERSION: 4.6.2` → `4.7.2`; the editor download, export-template download and the
`godot-mono-${{ env.GODOT_VERSION }}` cache key are all templated off that one line). `build.yml` was left
with `dotnet-version: 8.0.x` on purpose — the .NET 10 TFM is a separate, issue-gated step. The replay
goldens did not move: the sim is our own C#, so an engine bump cannot change deterministic output, and
the gate confirmed it (26 traces, 229,778 calls, ALL OK; 169/169 tests).

**.NET 10 cutover** (#112, PR #118, merged 2026-11-18). Both gates in #112 were verified before work
started: #111 merged, and Godot-MCP v0.40.0 (carrying #522 + #523, official .NET 10 support) had landed.
Across all five projects — `remake/game/OpenSimAnt.csproj`, `remake/src/OpenSimAnt.Sim`,
`remake/src/OpenSimAnt.Data`, `remake/tests/OpenSimAnt.Sim.Tests`, `remake/tests/OpenSimAnt.Replay` —
`net8.0` → `net10.0`; `remake/game/global.json` pins `10.0.404` (rollForward `latestFeature` unchanged);
`build.yml` and `release.yml` now use `dotnet-version: 10.0.x`; `tools/shots.sh` and `docs/NIGHTLY.md`
follow the new toolchain. The gate ran twice (after the code commits, then on the final pushed tree) —
build 0W/0E, **169/169 tests on net10.0**, **26 traces / 229,778 calls, ALL OK**, exit 0. The permanent
`com.IvanMurzak.*` pin at 8.19.0 (0.35.0-era) was deliberately untouched; the 0.40.0 addon that the
stable editor runs is the envelope's nightly experiment, pinned locally by the untracked
`remake/game/Directory.Build.targets` override, pending the owner-gated promote step.

One honest wart, and its closure: the net10.0 gate build overwrote the stable editor's last good
assembly (`.godot/mono/temp/bin/Debug/OpenSimAnt.dll`), which the .NET 8 editor cannot load — the

full verification (unit lines re-pointed at `~/.dotnet`, `/etc/profile.d/dotnet.sh` replaced,

build.

## Three capture artefacts, closed

The three known paint-lag / capture-side differences from Dev Log #1–3 are now all root-caused and
documented as capture-side, not code fixes:

- **Yard 9 px** (#25 / B18). The `yard` capture differed by 9 px at (264,195)..(289,200) — two
  object-shaped clusters: the dog's tail (x=288, rows 195..198) and a porch flower (x=264, rows 195..199).
  Template-matching against the archive sprites: the dog is frame **8510** (149/153 ink px; the 4 misses
  are exactly the tail), the human 8001 (219/219) — same frames as `yard.state`. The capture lags the
  State by one step, exactly the documented B16 kind. PR #104, no code change; the docstring and the
  ROADMAP B18 row carry the finding.
- **Yardfront 2 px** (#29 / B19). The `yardfront` capture differs by 2 px at the window's top-border
  end caps, (63, 83) and (576, 83) — yellow (255,242,4) in the original, black in the remake. The cause is
  a redraw-order artefact: a fresh RAISE repaints the frame and the content but not the edge columns, so
  the frame's yellow end-cap row shows; a full picture draw lays the bitmap's own black edge columns
  over x=63/x=576, including row 83 (`yard`, `house`, `strat`, `graphic`, `card` all 0 px). No state-based
  fix exists — the raise history is not in memory. PR #106, reproduced pixel-for-pixel by a fresh
  emulator run; documented in the compare tool's docstring.
- **Editfront / popup 32 px** (#55). The 32 px in the same 8×8 block at (432,102)..(439,109) — 16 light-grey
  (194,194,194) where the original has black and 16 black where it is grey — was misread as "a 50 % stipple
  drawn in the other phase." PR #110 makes the call: it is a single black nest ant (index 90, type 0x17, at
  cell (60,5) in the black-nest map in `editfront.state` / `popup.state`); the original capture draws the
  ant at (61,6) — one diagonal cell off. The remake renders the State (ant at (60,5)); the difference is
  the same one-step paint lag, not a stipple. Documented in the compare tool and the A5 doc.

A follow-up to B18 is worth naming: the dog's clip / sprite-layer path (`f_6feb3` → `DS:2A30`,
`G:10DA`/`G:10DC`, `f_272c2`) was traced end to end (PR #116, closing #103 / B20). `DS:2A30` is a
create-vs-update selector (not a clip parameter); the composite resolves records through the sprite layer
and blits the full picture width; the word passed as the "clip" (`[rec+0x16] & 7` = `x & 7`) is only a
sub-byte bit offset. Bitmap 8510 is a type-3 picture, 20 px wide, and its tail ink (palette 10, column 19,
rows 2..5) is what B18 found missing in the capture — confirming the missing tail is a lag, not a clip.
The note lands in `docs/SIM_NOTES.md` and the ROADMAP B20 row.

## File-dialog fixture work (#54)

The `filedlg` capture was the one window capture that could not be compared: `compare_screens.py` rendered
the dialog against whatever directory was on the machine, while the reference capture was made from the
directory as it stood when the original was recorded — 989 px differ at (170,125)..(266,162), the file
list itself. PR #86 made the pair comparable: the file dialog now lists `*.ant` case-insensitively, like
the original's DOS find, and compares against a fixed fixture (a handful of empty `*.ANT` files with fixed
names); `screens.py` records the same fixture names into its sidecar so the pair is comparable on any
machine. PR #88 closed the review's four notes: each capture whose flags carry `--file-dir=` gets its own
fixture rebuilt from its own `<name>.files` sidecar; the sidecar now records what was **served** (observed
listing, `/`-suffixed, sorted) rather than intended; `make_fixture` rebuilds over non-empty stray
subdirectories; and the A5 doc carries the corrected two-cause diagnosis (each side listed its own
directory; the remake's case-sensitive `*.ant` match listed no uppercase DOS names on Linux) and the
0-of-307,200-px result.

## The release.yml dev-log guard

PR #91 (merged 2026-11-15) added one step to the export job — **Require a dev log entry for the tag** —
right after checkout and before anything is built or published. It runs on the tag path only
(`if: github.ref_type == 'tag'`), asserts the checkout is at `$GITHUB_SHA` (so a post merged after the tag
cannot paper over it), and fails when no post in `docs/_posts/` **at the tagged commit** names the tag.
It is a hard gate with no override. The design was settled against the reviewer's comment on #62: the
acceptance text's date-keyed guard would pass vacuously (any second tag cut the same day as an existing
entry would satisfy it), so the check requires the tag name in a post body. The residual — a forward
reference can satisfy the key (at the v1.0.0 tagged tree, Dev Log #1 names "v1.0.0" once in "What's
next") — is named in the PR and deliberately not tightened. The guard proves the post is in the repo at
the tag; it does not prove the permalink answers 200 (Pages deploy), which stays the publish step's job.
