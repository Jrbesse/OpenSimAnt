# Dev Log #1 — Byte-Exact, or It Doesn't Count

*November 10, 2026*

This is the first entry of a dev log whose subject is a 34-year-old DOS game. That needs a reason, because
"remake SimAnt" is a one-line idea and this is not a one-line project.

The reason is that the interesting problem turned out not to be the game. It was **proving the game was
right**. A remake can be 95% faithful and feel wrong in a way nobody can name: the ants drift a little, the
queen lays a little faster, the lawnmower turns at the wrong moment. You cannot debug that by playing. So this
project is built backwards from verification — the emulator is the ground truth, the Python port is the
readable spec, and the C# remake is checked against the spec, call by call.

This entry is about that machinery, and about the two bugs it caught that no amount of play-testing would have.

---

## The state is the whole trick

The original is a Microsoft C 6.0, large-model DOS program, overlaid, built 6 December 1991. Its simulation
state lives in a single 64 KB segment at `0x3e1d`: the surface grid, the two nests' terrain and contents grids,
the ant arrays, the pheromone maps. Around it sit the constant tables at `0x3d57`, the far globals at `0x50f6`
and DGROUP at `0x55b3`.

The port does not model that state — it *is* that state. `simant_ref.state.State` is a `bytearray` covering flat
linear `0x3d570..0x62000` and exposes `u8`/`s16`/`set32` by `(segment, offset)`, exactly like the original's
addressing. **150,160 bytes.** When a routine returns, the check is not "did something sensible happen" but
"does every one of those bytes match what the original had".

That design decision is what makes everything downstream cheap. A snapshot of the original's memory, taken at
any point in a game, is a complete, runnable test fixture. There is no mock to maintain and no expected-value
table to write by hand.

## Three oracles, cheapest last

The verification ladder, in the repo's own terms:

1. **The emulator.** `tools/re/emu.py` boots `SIMANT.EXE` in Unicorn, plays a Quick Game from seed `0x1234`,
   and caches six snapshots — ticks 0, 300, 900, 1500, 2200, 3000. A ported routine is checked by restoring a
   snapshot, running the *original* function at its flat address, running the port on the same state, and
   diffing all 150,160 bytes. Arguments can be varied, rare states planted (`pre`, `pre_once`) to force branches
   a normal game never reaches.
2. **The Python reference.** Once a rule is verified against the emulator, it is the cheap oracle for everything
   after — no emulator boot, no snapshots.
3. **The C# replay.** The reference records every outermost call: arguments, hook class, clock, state before and
   after. The C# port is found by reflection (`surface.s_bored` → `Surface.SBored`), run, and compared. The
   current set is 26 trace files, roughly 225,000 calls and 67,200 `SimStep` ticks.

Two random number generators run in parallel and both had to be reproduced exactly: the game's own 16-bit Galois
LFSR at `DS:8ba2` (`x <<= 1; if carry, x ^= 0x1bf5`) and Microsoft C's `rand()` (`s = s * 214013 + 2531011`),
plus its `min(rand(n), rand(n))` variant that biases toward zero. Tick-for-tick fidelity also means drawing from
the LFSR at the same *moments* as the original — the spider composite, the speech balloons and the yard's rain all
consume numbers, and skipping one draw shifts the whole game.

Byte-exactness has sharp edges: 16-bit wraparound, C's truncating division and modulo, and short-circuit order in
conditions that read two globals. `_cdiv` and `_cmod` exist in the Python port purely so C semantics survive the
translation into a language whose `//` and `%` do not truncate the same way for negatives.

## Bug one: a table that was never needed until it was

The spider's food steps (`f_0c73d`) were ported, verified against twelve emulator cases, and shipped. Then the
default start of a Quick Game hung: the spider's state machine cycled forever.

The routine reads a step table at `DS:1B9A..1BA1`, eight bytes. The port read the table from the extracted game
tables — and those bytes were never in `gen_game_tables.py`, because no test had ever reached that path. Every
`--deps` run took a branch that skipped it. The port was correct and the data was missing, which is the worst
shape a bug can have: the code review passes.

The lesson is now a rule in the repo: **a port that reads `DS` must have its bytes in the table generator**, and
the way you find out is a replay from a default start, not a replay of the twelve cases you chose.

## Bug two: the glossary was one entry off

The SimAntipedia's bold words show a definition when clicked. In the remake, every word showed the definition of
the *previous* word.

`f_78440` reads the word at `4EE5:0500 + 0x22*i` — 34 bytes per entry — and the definition id at `+0x20`. The
port had the stride right and the field offsets off by one field, which is invisible in code that indexes an
array of structs by name and completely visible in a byte-diff. The fix touched the reference, the C# port's
`EmbeddedAssets` range (`0x4f350..0x4f6e6`), the pack builder's encoder, and the re-exported `original_pack.zip`.

Two lessons, both now written down: a port that reads `DS` needs its bytes enumerated, and an off-by-one in a
data layout is not a typo — it is evidence that the layout was inferred rather than decoded.

## The clean pack: 810 files so nobody needs the original

The legal position of a from-scratch remake is that it must not carry the original's art, text, sound or fonts.
So the project re-made all of it, clean-room, against written specs:

- **252 bitmaps** — yard, house screens, the SimAntipedia's 40 pictures, the map actors.
- **35 sound effects, 30 songs**, on 16 FM patches, rendered through a port of the original's sequencer.
- **34 window layouts**, **94 texts and 53 captions**, the glossary, the fonts.
- `clean_pack.zip` — **810 files**, built by `tools/clean_pack/build.py`, not tracked in the repo.

The game now runs on that pack with no original files at all, and CI plays six screens from it under `xvfb` on a
runner that has never seen `SIMANT.EXE`. The original-files path still exists and is still the reference: point the
game at your own copy and it looks and sounds like 1991.

The screens were compared too: 24 captures of the remake against the original on the same game state, 21
pixel-identical, the other 3 off by redraw timing. And a 200,000-tick long run with no divergence in state.

## What's next

- **The similarity review** (issue #20) — the clean pack judged against the original for anything too close, which
  is the gate before the pack can ship publicly.
- **Licences and the public decision** (#22), then **v1.0.0** (#23).
- **The last visual bugs**: the yard's front border still differs by 2 px at y=83, and a capture differs by 9 px
  at (264,195) — both in the "who cares" bucket until it is time to be exact about everything.

The simulation is done and matches. What is left is the part where the game becomes something other people can
have, and that is a paperwork problem wearing an engineering hat.
